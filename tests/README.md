# Pruebas de HSM

Pruebas end-to-end (Playwright) de `index.html`. Viven en esta carpeta aparte
para no mezclarse con el sitio: Vercel sigue desplegando solo `index.html` y
las imágenes de portada, nada de acá.

Cada archivo `*.spec.js` es un script independiente que abre el sitio en un
navegador real, hace clics como lo haría una persona, y al final imprime
cuántas verificaciones pasaron y cuáles no (termina con código de salida 0
si todo pasó, 1 si algo falló). No usan ningún framework de testing — es
JavaScript simple a propósito, para poder leerlos y modificarlos sin tener
que aprender una herramienta nueva.

## Cómo correrlas

```bash
cd tests
npm install              # una sola vez, instala Playwright
npm run install-browser  # una sola vez, instala el Chromium que usa Playwright
npm test                 # corre todas las pruebas, una por una
```

`npm test` levanta su propio servidor local (sirviendo el `index.html` de la
carpeta de arriba) en el puerto 8811, corre cada `*.spec.js` contra ese
servidor, y lo apaga al terminar. No hace falta tener nada corriendo de
antes.

Para correr un solo archivo puntual (más rápido mientras se prueba algo):

```bash
cd tests
python3 -m http.server 8811 &       # en otra terminal, o con & como acá
node roles-y-permisos.spec.js
```

### Variables de entorno (opcionales)

- `HSM_TEST_URL`: URL del sitio a probar, si no es `http://127.0.0.1:8811/index.html`.
- `PW_CHROMIUM_PATH`: ruta a un Chromium ya instalado, para no depender del
  que instala Playwright. Si no existe ese archivo, se usa el de Playwright.

El rango de años ("Desde"/"Hasta") ahora permite llegar hasta 2002, el límite real de los datos de la AIF, no solo 2014. **Juveniles es una categoría más de la lista, pero en un modo distinto**: como su historial ya está cargado a mano y aprobado, acá <strong>nunca se escribe nada como Juveniles</strong>, ni siquiera cuando un año no tiene nada cargado — siempre se le resta al total de la AIF (un solo total por año, sin separar por categoría) lo que ya está cargado como Juveniles ese año (`datosYaEnJuveniles`) MÁS cualquier otra fila ya registrada ese mismo año, tenga categoría puesta o no (`datosYaRegistradosAmbiguos`: ya están contadas, así que no hay que agregarles otra fila al lado con el mismo total y duplicar el año), y la diferencia SIEMPRE queda como una fila sin nombre de categoría, para revisar a mano; el año en curso nunca se toca con esta herramienta. (Bug real encontrado y corregido en este mismo desarrollo: la primera versión sí escribía "Juveniles" para los años sin nada cargado, lo que inflaba el total oficial de Juveniles para jugadores que en realidad venían de otra categoría esos años. Segundo bug real, encontrado con Retamar: `datosYaRegistradosAmbiguos` solo contaba filas SIN categoría puesta, así que si el jugador ya tenía una fila con una categoría puntual como Cadetes que ya explicaba el total de la AIF, esta herramienta no la veía y agregaba una fila "otra" con el mismo total al lado, duplicando sus totales de carrera — ahora cuenta cualquier fila que no sea Juveniles, tenga categoría puesta o no.) También bloquea el service worker por el mismo motivo que `aif-sincronizar.spec.js` |
| `ejercicio-posicion.spec.js` | Segmentación por posición en Entrenos (además de "con pelota"/"físicos"): al crear un ejercicio (de biblioteca o de pizarra) se puede marcar, con un chip, para qué línea del equipo es (Defensores / Mediocampistas / Delanteros), o dejarlo en "Todas" (sin marcar nada). No tiene relación con las posiciones puntuales de cada jugador (`POSICIONES`, en la ficha de cada uno) ni con asignar gente: es solo para que el DT pueda filtrar y encontrar rápido "ejercicios para defensores". En la biblioteca de texto es un filtro aparte, independiente del de fase. En la lista de pizarra, en cambio, "Ejercicios por posición" es un 4° botón del MISMO filtro general que ya tenía "Todos / Ejercicios con pelota / Ejercicios físicos" (excluyente con esos otros, no una categoría más del ejercicio): recién al elegirlo aparecen, como sub-filtro, las 3 macroposiciones (reemplazando ahí a la subcategoría de controles/recuperación/definición/etc.), y por defecto ("Todas") muestra los ejercicios que tengan marcada alguna posición, sin importar si son con pelota o físicos (reportado: la primera versión mostraba las 3 macroposiciones como una segunda fila de chips siempre visible debajo, separada del filtro de tipo, en vez de depender de él). Se ve como una etiqueta en la fila/tarjeta de la lista y en el detalle. Un ejercicio viejo sin el dato queda en "Todas" al editarlo (no se inventa una respuesta). El chip de la pizarra sigue el mismo patrón DOM-directo que paridad/jugadoresMin/Max (se sincroniza también en `view.pizDraft` para no perderse con los `render()` de elegir herramienta/color) |

## Qué NO cubren todavía

No hay pruebas de Firebase real (login, sincronización en la nube): el
sandbox donde se escribió esta app bloquea el acceso a Firebase/gstatic, así
que todo se prueba con el modo "sin conexión" (`hsm-sin-conexion`), que usa
los mismos datos pero guardados solo en el dispositivo. Si en algún momento
se prueba desde un entorno con acceso real a internet, valdría la pena sumar
pruebas de ese flujo.

Por la misma razón tampoco se puede probar la carga real de `pako` (la
librería que comprime la base antes de subirla a Firestore): el sandbox
bloquea también los CDN (jsdelivr, cdnjs), no solo Firebase. Lo que sí se
probó acá es la lógica de compresión/descompresión en sí (con un `pako`
fabricado a mano en `sincronizacion-en-vivo.spec.js`) y, aparte de estas
pruebas, el algoritmo de compresión (DEFLATE) contra una muestra de datos
con la forma real de la base, usando el `zlib` de Node: redujo unos
650 KB de JSON a poco más de 20 KB, con una vuelta exacta al original.

Tampoco hay una prueba end-to-end de `api/aif.js` (la función de Vercel que
trae el fixture real de aif.org.ar) contra la AIF de verdad: `run-all.js`
sirve `index.html` con un servidor estático de Python, que no ejecuta
funciones serverless, así que `aif-sincronizar.spec.js` simula la respuesta
de `/api/aif` con `page.route`. La lógica de `api/aif.js` en sí (los
endpoints de la AIF, el mapeo de categoría→torneo/división, el parseo del
JSONP) sí se probó a mano contra el sitio real en el momento de escribirla,
para las 5 categorías. Si la AIF cambia su estructura en el futuro, esta
función podría necesitar ajustes que estas pruebas no van a detectar solas.

## Reglas de Firebase (`reglas/firestore-reglas.test.js`)
